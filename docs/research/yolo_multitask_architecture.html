Architecture for FMD

01Executive summary

Bottom line
The lead's multi-head idea is technically sound and precedented. YOLOR (2021) proved a single shared representation can serve detection and multi-label classification simultaneously, with joint training beating single-task baselines. YOLO-Master (CVPR 2026) implements the modern version of this - but its classification branch is single-label softmax, COCO-format only, and OBB is unsupported, so it cannot be adopted directly. The recommended path is a custom dual-head model on the stable Ultralytics 8.4.142 codebase FMD already runs in production, borrowing YOLO-Master's design principles.
YOLOR / YOLOR-MTLconcept: high
  • Proved detect + multi-label cls in one model
  • Joint training improved all tasks
  • 2021-era code, unmaintained / paper-only
YOLO-Master MTdirect use: medium
  • Modern unified multi-task head + router
  • Preview status; classify is softmax-only
  • COCO format enforced; OBB raises ValueError
Custom dual-headrecommended
  • Multi-label sigmoid head for LP tags
  • OBB detection kept; YOLO txt labels kept
  • Built on stable 8.4.142, no preview risk

02The FMD two-tier label problem

FMD inspection produces two fundamentally different label types that today require two separate production models:

PropertyOOI - object of interestLP - lens presentation
Label typeOriented bounding boxes (OBB)Image-level tags, multi-label
Classes10 defect classes5 tags, 0-4 active per image
Dataset346 train / 88 val images3,377+ tagged images
FormatYOLO txtFolder-per-class / tag list
Production modelYOLO26n OBBResNet50 (single-label)
RoleFind and box each defectName the frame condition
The leakage problem
Current separate models sometimes classify LP-tag conditions as OOI defects and vice versa. A shared backbone learns one feature space for both tasks, so the classification head (whole-image view) and the detection head (local view) complement rather than compete - but the architecture cannot fix ambiguous label names or annotation noise. See section 16.

03D1-D4 metrics - undefined

Blocking issue
D1, D2, D3, D4 appear nowhere in the FMD repository or the knowledge base. All .md files in the analysis repo and every FMD-KB wiki page were searched - zero matches for D1-D4 as defect metrics. The lead's instruction ("classification head focuses on D3/D4, detection head on D1/D2") cannot be mapped to heads until she defines them. This is the only open question blocking architecture finalization.

04YOLOR - You Only Learn One Representation (2021)

Paper: Wang et al., arXiv:2105.13255, from the YOLOv4 team. The foundational result this whole direction rests on.

Core idea: one unified representation combining explicit knowledge (learned directly from data) with implicit knowledge (learned latent vectors that modulate features and predictions per task).

Three mechanisms, and what each would do for FMD

MechanismWhat it doesFMD relevance
Kernel space alignment Implicit vectors added to / multiplied with feature maps align feature distributions across tasks Aligns OOI and LP feature spaces so one backbone serves both
Prediction refinement Implicit vectors adjust outputs - box coordinates, anchor offsets, scores Frame-level LP context could refine per-defect confidence
Multi-task training Implicit knowledge in each branch enriches the shared space The mechanism behind "joint training beat every single-task baseline"
Why it matters here
Detection plus multi-label classification in one network is exactly the FMD pattern - and on COCO test-dev it held 55.4% AP at 30 FPS (V100) while improving every task through joint training.
Why not adopt directly
2021-era PyTorch codebase, unmaintained, pre-Ultralytics. Treat it as the design reference for our custom head, not as an implementation source.

05YOLOR-Based Multi-Task Learning (2023)

Paper: Chang, Wang, Wang, Chou, Liao, arXiv:2309.16921. Scales the YOLOR idea to four jointly trained tasks: object detection, instance segmentation, semantic segmentation, image captioning - with no pre-training and a low parameter count.

Key finding quoted: "Features extracted for a specific task are not generalized enough to be applied to other tasks." Multi-task learning forces the shared representation to generalize; a single convolutional layer with two learnable priors replaces YOLOR's heavier implicit-knowledge machinery.

FMD relevance: high, as a scaling precedent
It demonstrates the growth path: start with two heads (detect + LP classify), add more later (e.g. defect-grade classification) on the same shared representation. Note the code was promised as "released soon" and never fully published - design reference only.

06YOLO-P - ruled out

Not a multi-task architecture
YOLO-P is a modified YOLOv3-tiny with a DenseNet backbone for palm oil plantation detection (FFB, grabber, palm tree). "P" is for Palm. Single-task, agriculture domain, no classification head - nothing to borrow. The teammate's mention is almost certainly name confusion with YOLOPv2 (driving perception) or YOLO-R.

07Generalist YOLO (WACV 2025)

Architecture: unified GELAN encoder, primary-secondary co-attention, efficient prediction heads. Tasks: detection, instance/semantic/panoptic segmentation, captioning.

Key innovation: gradient masking - each task's gradients may only update the feature subset assigned to it, directly reducing task conflict during joint training.

FMD relevance: medium - one borrowable idea
If LP gradients destabilize detection (or vice versa) during joint training, masked gradients let each head own its feature subset. That is the same conflict we see as LP/OOI leakage today. The full architecture is far heavier than FMD needs; the training trick is the takeaway.

The classification branch - the critical limitation

classify branch - single-label by construction 
self.cv4_cls = nn.Sequential(
    nn.AdaptiveAvgPool2d(1),              # global average pool from P5
    nn.Flatten(),
    nn.Linear(cls_in, cls_in // 2),
    nn.SiLU(),
    nn.Linear(cls_in // 2, self.nc),       # SAME nc as detection
)
# loss: cls_global_loss = CrossEntropyLoss  ->  softmax  ->  ONE class per image
# output: class_logits [B, nc]

Three structural facts follow: one image gets exactly one class (softmax), the class count is shared with detection, and labels must arrive in COCO JSON with a cls_img field. FMD needs the opposite on all three counts.

12TaskRouter - from source

File: ultralytics/nn/modules/multitask/router.py. Routes features per spatial token so each branch sees features weighted toward its needs while a shared path keeps common semantics:

TaskRouter forward path (verified)
features [B, C, H, W]
affinity router
Conv(C, C/8, 1) - GroupNorm - SiLU - Conv(C/8, num_tasks, 1)
top-K soft blending
K=2 - softmax with temperature - 0.98 sparse + 0.02 dense exploration
task features
x * affinity -> [B, num_tasks, C, H, W]
+ shared path
cross_task_proj(x) -> common semantics preserved
Why TaskRouter matters for the leakage problem
LP tags are frame-level conditions; OOI defects are local regions. A router can learn to send global context toward the classify branch and local detail toward detection - exactly the separation that splitting the label space by hand tries, and fails, to achieve. This is the single most borrowable YOLO-Master component for FMD.

One genuinely good design decision
The unified data path preserves missing supervision instead of converting it to negative targets. An image with boxes but no classification label is not treated as "no class present" - its classification loss is masked out for that step. FMD needs exactly this: the OOI set (346 images) and the LP-tagged set (3,377+) only partially overlap. Section 15 copies this pattern.

15Recommended: custom dual-head YOLO

Build a custom dual-head model on stable Ultralytics 8.4.142. Keep the production OBB detection path untouched; attach a multi-label LP head on the P5 level of the neck. Head implementation sketch

lp_head.py - multi-label LP head + masked loss 
import torch.nn as nn

class LPClassifyHead(nn.Module):
    # Multi-label LP tag head: GAP on P5 -> FC -> 5 independent logits
    def __init__(self, c1: int = 1024, n_lp: int = 5):
        super().__init__()
        self.pool = nn.AdaptiveAvgPool2d(1)
        self.fc   = nn.Sequential(
            nn.Linear(c1, c1 // 4),
            nn.SiLU(),
            nn.Dropout(0.1),
            nn.Linear(c1 // 4, n_lp),   # 5 logits, independent
        )

    def forward(self, p5):
        return self.fc(self.pool(p5).flatten(1))   # [B, 5]

# Loss: BCEWithLogitsLoss - NOT CrossEntropy (multi-label, not single-label)
lp_criterion = nn.BCEWithLogitsLoss(reduction="none")
# Images with no LP annotation get a validity mask - the pattern borrowed
# from YOLO-Master's preserve-missing-supervision contract (section 13).
lp_loss = (lp_criterion(lp_logits, lp_targets) * lp_valid_mask).sum() / lp_valid_mask.sum()

Combined loss

loss composition 
L_total = L_obb                # standard YOLO26: box + cls + dfl + angle
        + lambda_lp * L_lp     # masked BCEWithLogits over the 5 LP tags

# lambda_lp starts at 1.0; sweep {0.1, 0.5, 1.0, 2.0}

# detection-only production baseline - the LP head must not tax detection

16The leakage problem - what the architecture can and cannot solve

CanCannot
Learn one shared representation for both tasks - YOLOR showed joint training improves every task over single-task baselines

Give LP a whole-image view (GAP) and OOI a local view (anchors) - structurally different views of the same image compete less

Route features per task (TaskRouter pattern): global context toward LP, local detail toward detection

Align feature spaces across tasks (YOLOR kernel alignment) so semantically similar labels stop competing 		Fix ambiguous names - "Missing Lens" existing as both an LP tag and an OOI class with different meanings keeps confusing any model

Fix label noise or annotation inconsistency

Fix the data ceiling: 346 OOI training images, 4-5px annotation noise

Fix the label-format mismatch (boxes vs image-level tags) - the loader must handle both correctly
The real fix is mostly data work
(1) Disambiguate label names so no LP tag and OOI class share a name. (2) Keep the frame-level vs object-level distinction explicit in the schema. (3) Add training pairs where LP tags and OOI defects co-occur on one image, so the model learns both signals together. The dual-head architecture then has structure to exploit - it cannot create it.

17Implementation roadmap

Phase 1 - Proof of concept (1-2 days)

Take the existing YOLO26n OBB model. Attach LPClassifyHead (GAP + FC(5) + sigmoid) to the P5 neck level. Train on 10-20 images carrying both label types for a few epochs.

Success criteria: both heads converge; detection mAP within noise of the detection-only baseline.

Phase 2 - Full pipeline (3-5 days)

Build the dual-format data loader: YOLO txt boxes + LP tag list per image, with a validity mask for images lacking LP annotations. Implement the combined loss with lambda_lp. Train on the full 346/88 detection split plus the LP-tagged set. Evaluate per-class AP for both heads; compare against the separate production models.

Phase 3 - Optimization (2-3 days)

Sweep lambda_lp. Optionally add a TaskRouter-style lightweight affinity branch on the neck. Add per-class loss weighting for imbalanced OOI classes. Measure end-to-end inference latency vs the current two-model pipeline.

Phase 4 - Production

Export to ONNX/TensorRT. Wire both heads into pass/fail logic: the edge algorithm stays binary pass/fail; this back-office model supplies the reason - which OOI defects and which LP tags drove the failure. A/B test against the separate-model pipeline before any switchover.
