# AGENTS.md

Working rules for this repository. Read this before starting.

## Docs and the board

- Every doc starts with a five line header:

  ```
  ---
  title: Crop margin sweep
  date: 2026-09-19
  type: result          # state | session | result | decision | report | experiment | protocol | method | reference
  status: active        # active | done | superseded
  where: reports/preprocessing/crop_margin.md
  ---
  ```

- `HANDOFF.md` is **state only**: the resume point, what is in flight, what is next. Rewrite it each
  session, never append to it. History belongs in `docs/sessions/<year>-W<week>.md` and in the topic
  docs.
- `docs/INDEX.md` is generated by `tools/index_docs.py`. Never edit it by hand, your edit is lost on
  the next run. Run the tool after adding, moving or renaming a doc. `--check` exits non-zero when a
  file has no header, which is the hook for a pre-commit gate.
- `docs/sessions/` holds one file per week. `docs/decisions/` holds one short file per decision
  (create it when the first decision lands). `docs/reference/` holds stable how-tos.

## Searching this repository

- `docs/archive/` is **superseded** material: audit trail only. Keep it readable by path, but never
  let it win a keyword search over current docs. The archived accumulated handoffs are 78-92 KB of
  near-complete project vocabulary, so under plain keyword matching they beat the short current doc
  for almost every query. That is how you end up answering from a retired rule.
- Coverage is not currency: a doc matching the words of a rule does not mean the rule still stands.
  Before quoting a doc, check its `status:` header and prefer the newest `docs/decisions/` file.
- Default search already skips archive: `rg` honours `.gitignore` and `.graphifyignore`, and
  `tools/index_docs.py` skips `status: superseded` (opt back in with `--include-status superseded`).
- Reaching archive is deliberate and explicit: `git grep`, `rg --no-ignore`, or read it by path.
  Do that when you are specifically after history, not when you want the current answer.
- After changing code run `graphify update . --force` (plain `update` silently refuses to shrink a
  stale graph), then `graphify query "<question>"` first. The graph holds no archive nodes.

## Reader-facing artifacts (reports, workbooks, decks, messages)

Anything a lead or a client will read is written for them, not for us.

- **No internal names.** No file paths, script or run-folder names, ticket ids,
  branch names, version tags ("rev2", "v3") or references to our decision log.
  The reader cannot resolve them, and they make the artifact look unfinished.
- **If a name must appear, define it where it appears.** Class codes from the
  annotation guide are fine because the guide defines them; add a one-line
  meaning in the same sheet or column note. Internal tool names are not fine.
- **Result first, method last.** The artifact states the number and what it
  means. How it was obtained gets at most one plain sentence ("counted from
  the annotated pictures"). The detailed method stays in our internal docs.
- **Every sheet or page opens with one plain line** saying what it shows, and
  every count names its population in the header ("pictures examined",
  "pictures used for training and testing").
- **Define unavoidable terms once**, on a definitions page or in the first
  note where they appear (tag, marked object, size flag, Clear).
- **No role attribution.** See the rule in the `simple-english` skill: never
  write "the lead said", "the client wants" or "our side" in a shared
  artifact. Write "the requirement", "the agreed limit", "the open point".
- The five-line doc header is for repository docs only; a workbook page does
  not carry it.

## The Notion Work OS board

- The board shows state; this repository holds the facts. A push writes titles, notes and numbers
  only. It never writes Status, Done or Timeline, so a tick made on the board is never overwritten.
- One row in **Work log** is one thing asked of us, from arrival to done. One row in **Results** is
  one result we have to be able to quote quickly. **Notes** are short pointers into this repo.
- `notiondocs.md` stages what goes on the board: one line per thing, a timestamp, and a permanent id
  (`wl-####`, `res-####`, `note-####`). Append only, newest first. It is local only and never pushed.
- Nothing goes to Notion straight from the repo. Mark an entry `verified` after checking it against
  the evidence, then push it, then write the Notion page id underneath that entry.
- Never edit an entry that is already pushed. Corrections are a new line that names the id it corrects.
- If an entry needs more than one line, it is a doc, not an entry. Put the detail in a doc and let the
  entry point at it.

## Hermes profiles: where work runs

Work on this repository is done by named Hermes profiles, not by one general agent. A profile carries its own model, memory and skill set, so a task is routed to the role that owns it. Profiles live outside the repository; this section records only which role owns what.

| Profile | Owns | Route work here when |
|---|---|---|
| `default` | Interactive work: code, docs, analysis | Anything the rows below do not cover |
| `orchestrator` | Decomposition and routing | A request spans several steps or several files |
| `ml-runner` | VM training and evaluation runs | An experiment has to be launched or measured |
| `researcher` | External evidence with citations | The answer is in the world, not in this repository |
| `learning` | Unassigned | Nothing yet. It has never been given a task. |

Rules:

- **One executor per file.** A card or session owns the files it touches. Never run a generator such as `tools/index_docs.py` while another worker owns `docs/INDEX.md`. `--check` writes as well as checks, so it is not a safe concurrent read.
- **The orchestrator routes, it does not execute.** A router that starts editing files becomes a second writer on the same file, which is exactly the failure the routing exists to prevent.
- **`ml-runner` writes one `run.json` per run**, beside that run's artifacts, and never hand-edits it. The schema is fixed and includes `status` (ok, failed or crashed) and `metrics.primary`, the single number a report should lead with. A crashed run writes `status: crashed` with the traceback path in `notes`; it does not omit the file. This is the uniform source that `experiments/registry.json` is regenerated from. Before it existed, CNN runs wrote a per-arm `metrics.json` while YOLO runs wrote a `batch1_summary.json` array, so there was no common shape to regenerate from and the registry was only reproducible for one family.
- **`ml-runner` runs on the VM only through `vm/ops/`**, piping the script over SSH so nothing loose is left on the shared box. The repository tree there is `/home/pranayp/fmd-analysis`.
- **`ml-runner` does not write reports or decks.** It emits the run record and stops. The report is a separate step gated behind the run, and it follows the reader-facing rules above.

Two skills carry rules that cross profiles. Load them rather than restating them: `verifier` (check a finished claim against the artifact, and sweep the diff for leaked secrets) and `vault-curator` (what may be written to the external knowledge base).

## Never pushed

`notiondocs.md` and anything under `run/`, `model_runs/`, `.obsidian-vault/` or `data/incoming/`. The
repository's `.gitignore` is the source of truth.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships. In this repo `graphify-out/` is gitignored — it is local only, never committed; rebuild it with `graphify extract . --code-only`.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
