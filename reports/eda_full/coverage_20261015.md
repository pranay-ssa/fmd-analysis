# Coverage analysis, what is annotated out of what exists

Ticket 015 of the full-coverage EDA map. Every number is keyed on the content
md5, never on a path, because 187 basenames hold a content that also exists under
a second name. Every number says whether it is a MENTION count (some annotation
file lists the picture) or a SHAPE count (the resolved label set holds at least
one shape for it). The word "annotated" alone is never used.

## Headline

Out of 10,614 distinct pictures in the census:

- **6,690 are mentioned** by at least one of the 9 annotation files. That is 63.0
  percent of the 10,614 census pictures. This is a MENTION count.
- **4,782 carry at least one shape** in the resolved labels. That is 45.1 percent
  of the 10,614 census pictures. This is a SHAPE count.
- **3,924 are mentioned nowhere**, that is no annotation file lists them. 37.0
  percent of the census. This is a MENTION count.
- **5,832 carry no shape**, that is 54.9 percent of the census. This is a SHAPE
  count, and it is not the same set as the 3,924, because 1,908 pictures are
  mentioned but carry no shape.

Contradiction called out: the map's Notes say "5,832 are mentioned nowhere". That
figure is the no-shape count (10,614 less 4,782), not the no-mention count. The
genuine no-mention count is 10,614 less 6,690, which is 3,924, and it is the
figure `resolution.json` carries as `unannotated_pictures`. Both the 5,832
(no shape) and the 3,924 (no mention) are reported below, named, so neither is
read as the other.

## How a picture is placed

One path per picture (map decision 6). A picture is placed in the folder of its
winning_path, the first library folder that holds it in the fixed order Updated
ICube Objects, then Updated Categorical, then ICube Defects Library. So the
per-folder, per-group and per-line strata partition the census, and their
distinct-picture counts sum to 10,614. The production image folder is not a
library folder and adds no picture, so it is not a stratum.

## 6. The folder-label disagreement, re-derived

The published figure is in `docs/cvat_production_20260925_pull.md`: the three
library folders label 113 images differently from each other. Its stated
breakdown is 35 Bubble vs Clear, 30 Wet Package vs Clear, 16 Dirty Strobe vs
Clear, 14 Bubble Cluster vs Clear, 10 Low Dose Obstructing Region of Interest vs
Low Dose, plus Fiber vs Extraneous Polymer and HEMA Fragment vs HEMA.

Re-derived here from the folder structure and the files, by content md5 as the map
requires, three ways:

| Route | Scope | Result |
|---|---|---|
| Content md5, class differs across the library folders | whole library, duplicates folder dropped | **279** |
| Content md5, same key | production batch only | **129** |
| Basename, class differs across the library folders | production batch only | **114** |

The published 113 is close to the basename route over the production batch, 114,
which is the route a pre-move check would take: it compares the same file name
across folders rather than the same content. That route reproduces the published
breakdown nearly exactly: Bubble vs Clear 35 (published 35), Wet Package vs Clear
32 (published 30), Dirty Strobe vs Clear 16 (published 16), Bubble Cluster vs
Clear 14 (published 14), Low Dose Obstructing Region of Interest vs Low Dose 10
(published 10). The one-picture gap between 114 and 113 is a single row, and the
Wet Package pair is 2 lower in the record than the file set holds now.

On the map's rule, content md5, the number is larger, not smaller. Over the whole
library it is 279, because the same content sits in more than one class folder far
more often than a name match can see: the old library files 90 pictures in Low
Dose Obstructing Region of Interest whose content the Updated Categorical folder
files as Low Dose, where a name route sees 10. Over the production batch by
content it is 129 against the name route's 114, and the extra rows are the 187
aliased basenames the name route cannot see.

So the figure differs, and here is why, stated rather than quietly updated: the
published 113 is a name-based count restricted to the production batch; on the
map's content rule the whole-library count is 279 and the batch count is 129. The
map note that a path or name count undercounts is exactly what happens here. The
pictures themselves, with the class labels side by side, are in
`run/eda_full_20261015/folder_disagreement.csv`, 279 rows, each carrying the class
in each of the three library folders.

The published 113 is not silently replaced: the record of 2026-09-25 stands as the
name-based figure it was, and the content-based figures are reported beside it.

## 8. Numbers that contradict something already published

Called out, not silently replaced.

- **5,832 "mentioned nowhere".** The map and the label-resolution record use 5,832,
  but it is the count that carries no shape, not the count with no mention. The
  count with no mention is 3,924. Both are reported, named, in every table above.
- **113 folder-label disagreements.** Re-derived as 279 by content over the whole
  library, 129 by content over the production batch, and 114 by name over the
  batch. The published 113 is the name-based batch route and stands as that. See
  section 6.
- **8,409 tagged pictures.** The 2026-09-17 pooled dataset split the census into
  8,409 tagged plus 2,205 Clear. That is a pool of pictures assigned a class by
  dataset rules, not a count of pictures that carry an annotation shape. On the
  resolved labels only 4,782 pictures carry at least one shape, and 6,690 are
  mentioned. The 8,409 is not reproduced here and does not match the resolved
  shape count; it belongs to the pooled dataset effort, which the map keeps out of
  scope.
- **177, 1,047, 10,614.** These three agree with what was published. 177
  library-only pictures, 1,047 production files (1,046 distinct contents, all
  matching the library by content hash), and 10,614 distinct census pictures.

## 9. How it was checked

Triple check, as the map requires.

1. Builder self-checks: 15, 0 failed. The folder, group and line strata each sum
   to the census 10,614; the mentioned, no-shape, nowhere and library-only totals
   match hand-typed values; the shape set is a subset of the mention set.
2. Verifier, a second route: 35 checks, 0 failed. The XMLs are parsed with
   `iterparse` rather than `ElementTree.parse`, the per-folder, per-group and
   per-line numbers are recomputed from scratch and diffed against `coverage.csv`
   row by row, and the folder-label disagreement is re-derived three ways with
   hand-typed expected values.
3. Byte-identical rebuild. Two consecutive runs of the builder give the same md5:

   ```
   coverage.csv              02daca54ae128938d77e3ed21aa659a1
   folder_disagreement.csv   240f7ad1002d7e063b105c19672cd095
   ```

Nothing was pulled from blob storage. Nothing was written to the shared VM.
